### A-01 · critical · The density scale is silently thrown away

**FIXED** at `72f2f218` — the factor is applied inside `checkDisplaySize` through the `VrDisplay` registry, which clamps anything outside 0.5–4 back to 1. Device check still owed.

`VrDensity.apply()` multiplies `AndroidUtilities.density` in `QuestApplicationLoader.onCreate`
(`TMessagesProj_AppQuest/.../QuestApplicationLoader.java:23`). Then
`AndroidUtilities.checkDisplaySize` reassigns it from the display metrics:

```
AndroidUtilities.java:2751   density = context.getResources().getDisplayMetrics().density;
```

and is called from `LaunchActivity.java:409` (activity `onCreate`, before any UI),
`LaunchActivity.java:7117` (`onConfigurationChanged`) and `ApplicationLoader.java:382`. The
multiplication happens once, before all three; the first one erases it. **The readability
feature this fork is named for does nothing in the shipped APK.**

Fix: apply the factor *inside* `checkDisplaySize`, immediately after the assignment and before
`newDensity` is read (the method compares old and new density to decide on
`Theme.reloadAllResources`, so a factor applied after that comparison would fight it). Do it
through a registry the headset build fills — the same shape as `VrPolicy` — so other flavours
see a factor of 1. Verify by logging `AndroidUtilities.density` after `LaunchActivity.onCreate`
and by measuring one `dp(64)` view in pixels on the device.

### A-02 · high · Half the notifications never meet the gate

**FIXED** at `72f2f218` — the gate moved into `appendMessage`, before the de-duplication loop. Device check still owed.

The gate sits in `processNewMessages` (`NotificationsController.java:1055`), which handles
**live** updates. There is a second intake: `processLoadedUnreadMessages`
(`NotificationsController.java:1515`), which runs when the client starts or reconnects, loads
what is unread, calls `appendMessage` at `:1583` and `:1671`, adds to `total_unread_count` at
`:1686`/`:1691`, and shows notifications at `:1720`. On a headset that sleeps and wakes, this is
the *dominant* path — and it bypasses the silence profile entirely. The first thing a user sees
after putting the headset back on is the stack of banners the product promised not to show.

Both paths converge on one private method:

```
NotificationsController.java:1371   private void appendMessage(MessageObject messageObject)
callers: 1245 (processNewMessages), 1583 and 1671 (processLoadedUnreadMessages)
```

Fix: move the `VrPolicy` call into `appendMessage` and remove it from `processNewMessages`.
One hook again, now at the true choke point. `total_unread_count` in the loaded-unread path is
computed from the `dialogs` argument, not from `pushMessages`, so the launcher badge is
unaffected — state this in the code comment, because the next reader will ask.

### A-03 · high · The digest is write-only and holds onto message spans

**FIXED** at `31a8273b` — `DigestActivity` exists and is reachable; `lastText` is a truncated `String` and entries cap at 200 dialogs.

`Digest` accumulates suppressed messages, but nothing reads it: `digest()` has no callers
outside its own declaration. There is no digest screen (SCR-24), no count in the header. The
whole reason to suppress rather than drop — "you can see what accumulated" — is unimplemented.

Also `Digest.Entry.lastText` is a `CharSequence` assigned from `message.messageText`
(`Digest.java:24`, `:46`). Telegram's message text is frequently a `Spannable` carrying
spans that reference other objects; keeping it alive for the session is a retention leak.
Store `String.valueOf(...)`, truncated.

### A-08 · medium · Tablet layout is undecided, and the density fix will decide it by accident

**MEASURED 19 September 2026 on a Quest 3, and the premise below was wrong.** The panel reports
**`sw640dp`**, above the 600 threshold, so **the app runs in tablet mode** — and it does so
*whatever* the headset scale is set to.

The reasoning in the original finding assumed that multiplying density by 1.54 would divide the
panel's dp width and could drop it under 600. It cannot. The multiplier is applied to
`AndroidUtilities.density`, which governs what `dp()` returns inside the app; the system
`Configuration` that decides resource qualifiers is untouched and keeps reporting 200 dpi and
`sw640dp`. So the two are independent: the interface is drawn 1.54× larger *and* Android hands
it the tablet resource set. Confirmed from both sides — `dumpsys activity activities` prints
`sw640dp w1024dp h640dp 200dpi`, and `aapt2 dump resources` on the built package prints
`bool/isTablet` as `() false` / `(sw600dp) true`.

What that costs is still open, and it turns on a second condition: `LaunchActivity`'s onMeasure
takes the two-column branch only when `!AndroidUtilities.isInMultiwindow`, and the panel's
windowing mode **is** `multi-window`, so the split is most likely collapsed into one full-width
column. That last step is unmeasured — the split layout only appears once an account is signed
in, and the sign-in screen is not it.

The decision, when it is taken, needs no new code: upstream already carries
`SharedConfig.forceDisableTabletMode` (`SharedConfig.java:262`, read at `:627` with default
`false`, toggled at `:1384`), and `isTablet()` is `isTabletInternal() && !forceDisableTabletMode`
(`AndroidUtilities.java:2980`). Defaulting it to `true` in the headset build is a one-line
change behind the same kind of inert seam the density fix uses. **Do not make it before seeing
the signed-in layout**, because on this panel the platform may already be doing the right thing,
and a switch flipped against a measurement nobody took is how the original premise here went
wrong. *Answered in full on 19 September, from inside the headset.* Signed in, the panel showed the
menu eating roughly three fifths of the width with the conversation squeezed into the rest — so
`isInMultiwindow` is **not** what the windowing mode suggested, the split does happen, and the
guess above was the right thing to refuse to act on. The fix is the switch this finding already
named: `VrLayout` (headset module) sets `forceDisableTabletMode` once per install, leaving the
two-column layout reachable from the headset settings for anyone who wants it. Confirmed on the
device after restart — `mainconfig.xml` reads `forceDisableTabletMode=true`. A third mode, a
narrow rail of avatars beside an open chat, was asked for in the same breath and is **P-19**.

### A-19 · high · The headset interface was English forever, and a folder of Russian pretended otherwise

**FIXED** — every one of the module's 56 string reads now goes through `LocaleController`, and
the folder that could never ship was deleted.

Found while checking that the dictation screen's strings reached the package. They did; nothing
Russian ever had. `TMessagesProj_AppQuest/build.gradle:124` carries upstream's
`localeFilters += ["zz"]`, which strips every Android locale from the APK, because Telegram
serves its own language packs at runtime instead. `values-ru/strings_vr.xml` was compiled and

`build/intermediates/merged_res/questDebug/mergeQuestDebugResources/values-ru_values-ru.arsc.flat`

### A-20 · high · The interface scale was derived from a panel that does not exist

**FIXED** — the scale is re-based on the measured panel, the default is the platform's own
density, and the setting now states its consequence in chats rather than in adjectives.

Reported from inside the headset once the layout was single-column: *«видно только четыре чата
и много по ширине»*. The arithmetic reproduces it exactly, which is how we know the model is
right and the number was wrong:

```
panel            800 px tall, system density 1.25
old factor       1.54           -> app density 1.925 px/dp
height in dp     800 / 1.925    =  415.6 dp
minus chrome     - 48 action bar - 44 folder strip
over DialogCell    / 70 dp      =  4.6 rows        <- "four chats"
```

`VrDensity`'s own header stated the premise: *"the panel is 1440x900 dp at 1.3 m covering 52
degrees, so one dp is 0.881 mm, which is 2.33 arc-minutes"*. The real panel is **1280×800 px at
200 dpi** — 1024×640 dp before any scaling of ours. The derivation was arithmetic on an invented
measurement, and the invented figure was larger than reality in exactly the direction that costs
content.

**What changed.** The steps are now absolute multipliers on the system density — `0.85`, `1.0`,
`1.25`, `1.54` — instead of `{0.85, 1.0, 1.2} × 1.54`. The default is **1.0**: the density the
platform already chose for a panel. The old 1.54 survives as the largest step for anyone sitting
far from it, because a headset panel is virtual and its angular size is the wearer's to change by
moving it — a better lever than a constant compiled into an app. The preference key is renamed
`density_step_v2`, deliberately, so a saved "normal" from the old scale cannot silently become
the largest step.

**What it buys, by the same arithmetic, now pinned in `VrDensityTest`:** 9 rows at 0.85, **7 at
the new default**, 6 at 1.25, 4 at the old one. The regression test asserts the old default still
produces 4, so any future change that walks the default back there fails in CI rather than in a
headset a day later.

**And the setting says so.** The density row and its chooser read *"Balanced — about 7 chats"*,
with the count computed from the panel in front of the user through a pure
`VrDensity.rowsForFactor(panelHeightPx, systemDensity, factor)`. A scale named only by size asks
a person to imagine the result; this one states it, and the thing it states is exactly what was
complained about.

**Not changed:** `MIN_TARGET_DP` stays 64 and is still never multiplied by the step. Ray jitter is
a property of the hand; trading legibility for rows is the user's call, a smaller hit target is
not.

### A-21 · high · The panel was landscape because this fork asked for landscape

**FIXED** — the headset manifest now declares `portrait`, and Horizon OS reshaped the panel from
**1280×800** to **500×800**.

Reported from inside the headset after the scale was re-based: the list was fine top to bottom,
but a message stretched across the whole width, so a chat showed one long line and almost nothing
vertically. A messenger is a tall column of short lines — that is why every phone client is
shaped like a phone.

The cause was ours, one line, and it had a comment defending itself:

```xml
<!-- Landscape and resizeable: the system owns the panel's size, the app must not fight it. -->
android:screenOrientation="landscape"
```

The comment was true and was then used to justify its own opposite. Horizon OS sizes a 2D panel
**from the orientation the app declares**, so declaring landscape is precisely how an app fights
for a shape — and the shape it won was wrong. `resizeableActivity` stays `true`, which is what
"the system owns the size" was supposed to mean.

**Measured after the change:**

```
before   mBounds=Rect(0, 0 - 1280, 800)   sw640dp w1024dp h640dp  lrg land
after    mBounds=Rect(0, 0 -  500, 800)   sw400dp  w400dp h640dp  nrml port
```

400 dp wide is a phone. Two consequences worth naming:

- **`sw400dp` is below the 600 threshold**, so Android no longer hands the app the tablet
  resource set at all. A-08's `forceDisableTabletMode` default is now belt-and-braces rather
  than the only thing standing between the user and a split panel — worth keeping, because the
  panel is resizable and a wide one would cross the threshold again.
- **The row count helper was wrong the moment the panel turned**, and it was caught here rather
  than by a user: `panelHeightPx()` took `min(displaySize.x, displaySize.y)`, which is the height
  only in landscape. In a 500×800 portrait panel the smaller side is the *width*, so every
  density step would have advertised four chats instead of seven. Now it reads `displaySize.y`,
  which is the height in whatever orientation the panel is in, and the test constant carries a
  note saying the height is 800 either way.

### A-22 · medium · Every cold start flashes a white panel

**FIXED** — the headset build launches into Telegram's own night background instead.

Upstream's `Theme.TMessages.Start` (`TMessagesProj/src/main/res/values/styles.xml:6`) inherits
`Theme.AppCompat.Light` and sets `android:windowBackground` and `android:colorBackground` to
white, so the launch window is white until the first frame is drawn. On a phone that is a blink.
In a headset it is a lit panel at arm's length, usually in a dark room, in a client whose entire
premise is staying quiet and dark — and the device's own configuration reports `night`.

**The fix is a new style name, not an override, and that was learned the hard way.** Redefining
`Theme.TMessages.Start` in the headset module was tried first and *lost the resource merge*: the
module's own `packaged_res` and the incremental merge directory both held our version, and
`aapt2 dump resources` on the built APK still reported
`parent=style/Theme.AppCompat.Light` with `size=11` and white backgrounds. Rather than argue
with the merge, the headset build declares `Theme.NicegramVR.Start` and points
`android:theme` at it from its own manifest with `tools:replace`. Verified in the package:

```
style/Theme.NicegramVR.Start  parent=style/Theme.AppCompat
  android:colorBackground   = @color/vr_launch_background   (#0E1621)
  android:windowBackground  = @color/vr_launch_background
AndroidManifest  application  android:theme = @0x7f110135   <- that style
```

The colour is Telegram's own night background, so the launch window and the first drawn frame
are the same value and there is no step between them.

**Worth keeping as a rule:** an app module redefining a library's style by name is the obvious
move and it silently did not work here. Check the built artefact, not the merge directory.

### A-23 · high · The brand accent lasted exactly one session

**FIXED** — the colour is now re-asserted on every start, because nothing persists it.

Caught on the headset immediately after the theme shipped, and the build could not have shown
it. `VrTheme` set the Night theme's accent 10 to `#8B5FF2`, selected it and saved. The device
then reported:

```
$ adb shell run-as my.nicegram.vr cat shared_prefs/themeconfig.xml
    <int name="accent_current_night.attheme" value="10" />     <- the selection persisted
    (no colour anywhere)                                        <- the colour did not
```

Two causes, one behind the other. The first was mine: `saveThemeAccents(theme, true, false,
**true**, false)` — `indexOnly=true`, copied from `ThemeActivity` where only the selection
changes. The second survives fixing the first: with `indexOnly=false` upstream does write
`accents_night.attheme`, and decoding that blob on the device gives
`09 00 00 00 00 00 00 00` — an id record with **no palette in it**. Upstream keeps accent 10's
colour in a literal array in `Theme.java` and rebuilds it at startup.

So a slot repainted once reverts on the next launch, and the brand colour would have been
visible only in the session that set it — the sort of defect that survives every test, every
package inspection and a first glance on a device.

**The fix separates the two acts.** Selecting accent 10 stays a first-run default, so a user who
picks another accent keeps it. Setting slot 10's *colour* happens in
`QuestApplicationLoader.onCreate` on **every** start, so whoever has that slot selected always
gets Nicegram's purple rather than a slot that means one thing today and another tomorrow.

**The lesson is the one this repository keeps relearning:** the artefact is not the evidence.
The APK carried the right code and the right colours; only the device showed what the code did
on the second run.

### A-24 · high · The dark theme was applied on every start and saved on none

**FIXED** — `applyTheme(night, true, **false**)`, and auto-night turned off once at install.

The operator reported the theme "being overwritten, and it is not clear why". It was not being
overwritten: it was never written. `VrTheme.applyDefaults()` called

```java
Theme.applyTheme(night, /* save */ true, /* nightTheme */ true);
```

and upstream's own body of that method is

```java
if (!nightTheme && save) { editor.putString("theme", themeInfo.getKey()); }
```

The third argument does not mean "this is a dark theme". It means "this is the theme to use
*at night*" — and it **skips the branch that persists the choice**. So the theme was correct
for exactly as long as the process lived, and the next cold start read no `theme` key and fell
back to Telegram's default.

A second mechanism worked in the same direction. `selectedAutoNightType` defaults to
`AUTO_NIGHT_TYPE_SYSTEM` on SDK 29 and above (`Theme.java:4252`) and Horizon OS is 34, so the
client followed the headset's own day/night state and could switch away from whatever had been
chosen. It is now set to `NONE` once per install — a default, not a lock: a user who wants the
system to drive the theme can still say so in settings.

Measured, on the simulator, in the file that decides it:

```
$ adb shell run-as my.nicegram.vr cat shared_prefs/mainconfig.xml | grep theme
    <string name="theme">Night        <- present for the first time
```

Before the fix that line did not exist at all. The same class of defect as A-23, one line above
the line A-23 fixed: **an argument whose name describes the theme, not the call.**

**Deliberately not changed, with the reason recorded so it is not re-opened as an oversight:**
the on-device media folders (`Telegram Images`, `Telegram Video`, `Telegram Documents`, and the
`Telegram` root under them) keep their names. Renaming them means editing about thirty literals
across seven upstream files — including `FilesMigrationService`, whose entire job is moving
files between two paths named by exactly these strings. The visible gain is a folder name in a
file browser a headset user rarely opens; the risk is a botched migration losing somebody's
downloads. Also unchanged: the permission-rationale dialog that the simulator shows at sign-in
("Please allow Nicegram VR to receive calls"). On the simulator — an emulated phone —
`AndroidUtilities.isSimAvailable()` is true; on a Quest 3 `getPhoneType()` returns
`PHONE_TYPE_NONE`, so the dialog cannot appear, and the telephony permissions are stripped from
the manifest anyway. Patching upstream for a simulator artefact would be the wrong trade.

### A-26 · high · Seven of the renames were written, compiled, and never reached a screen

**FIXED** — `formatString` and `formatSpannable` now pass through the same seam.

`VrBrand.rename` was installed in `LocaleController.getStringInternal`, described in its own
comment as "the one point every drawn string passes through". It is not. A string that carries
an argument is resolved by `formatString` (LocaleController.java:1671) and by
`formatSpannable` (:1715), each of which repeats the whole cloud-pack-then-resource lookup
**inline** and never calls `getStringInternal`. So every rename with a `%` in it was inert:

```
TelegramVersion                  "Telegram %1$s"                 <- the version line in Settings
TelegramCacheSize                "%s Telegram Cache"
LocalDatabaseSize                "%s Telegram Local Database"
StorageUsageTelegram             "Telegram uses %s of your device storage."
StorageUsageTelegramLess         same
VoipInCallBrandingWithName       "Telegram Call to %s"           <- the banner during a call
VoipInVideoCallBrandingWithName  "Telegram Video Call to %s"
```

Seven of thirty-five. Two of them are the first line a user reads on the settings screen and
the label on an active call — the places most likely to be looked at, renamed in the source and
unchanged on the device.

**The lesson repeats A-23's, one level up.** "Every string passes through here" was asserted
from reading one method rather than from following every caller, and the compiler cannot
contradict a rename that simply never runs. The check that would have caught it is the cheap
one: for each renamed key, does its value contain a `%`?

### A-27 · high · A round video was sized from the display and drawn into the panel

**FIXED** — sizes derived from `displaySize` are recomputed while the window is not the display.

The operator reported that round video messages are cut off inside the chat. The cause is one
`== 0`. Upstream computes `roundMessageSize`, `roundPlayingMessageSize` and
`roundSidePlayingMessageSize` **once**, guarded by `if (roundMessageSize == 0)`
(`AndroidUtilities.java:2798`), on the assumption that the first configuration a process sees
is the one it will live in. On a phone that holds. On Horizon OS it does not, and the client's
own log says so:

```
$ adb logcat | grep 'display size'
density = 1.25 display size = 2064 2208 …   <- the first call: the application context, the DISPLAY
density = 1.25 display size = 525 900  …    <- every call after: the activity, the PANEL
```

The first line is the one that runs while `roundMessageSize == 0`. So the size was fixed at
`min(2064, 2208) × 0.6` = **1238 px** — and the panel measured by the window manager in the
same session is **525 × 900**. A round video more than twice the width of the window it is
drawn into is a round video with its sides cut off, which is exactly what the device showed.

The panel geometry is confirmed from the other side too: `dumpsys activity` reports
`mBounds=Rect(452, 110 - 977, 1010)` — 525 × 900 at 200 dpi — while the default display is
2064 × 2208 at `sw1651dp`.

**The fix does not change the arithmetic**, which is upstream's and correct; it lets the
arithmetic run again on the configuration that matters. The guard becomes
`roundMessageSize == 0 || VrDisplay.windowed()`, and `windowed()` is false on every flavour
that has not installed a scale, so a phone recomputes nothing. `roundMessageSize` then becomes
`min(525, 900) × 0.6` = 315 px, which is 252 dp in a 420 dp panel.

`roundMessageSize` was also added to the display log that already prints density and display
size. This class of defect — a value frozen from the wrong configuration — is invisible in a
build, in a package and on a first glance at a device; one more term in a line that is already
printed makes the next one readable.

**Third instance of the same pattern**, after A-20 (a scale derived from a panel that did not
exist) and A-23 (a colour that lasted one session): *the first thing the process sees is not
the thing the user sees.* On this device the application context and the activity context
describe different rectangles, and anything cached from the former is wrong.
