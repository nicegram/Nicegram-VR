### A-01 · critical · The density scale is silently thrown away

**FIXED** at `72f2f218` — the factor is applied inside `checkDisplaySize` through the `VrDisplay` registry, which clamps anything outside 0.5–4 back to 1. Device check still owed.

`VrDensity.apply()` multiplies `AndroidUtilities.density` in `QuestApplicationLoader.onCreate`
(`TMessagesProj_AppQuest/.../QuestApplicationLoader.java:23`). Then
`AndroidUtilities.checkDisplaySize` reassigns it from the display metrics:

```
AndroidUtilities.java:2751   density = context.getResources().getDisplayMetrics().density;
```

and is called from `LaunchActivity.java:409` (activity `onCreate`, before any UI),
`LaunchActivity.java:7117` (`onConfigurationChanged`) and `ApplicationLoader.java:382`. The
multiplication happens once, before all three; the first one erases it. **The readability
feature this fork is named for does nothing in the shipped APK.**

Fix: apply the factor *inside* `checkDisplaySize`, immediately after the assignment and before
`newDensity` is read (the method compares old and new density to decide on
`Theme.reloadAllResources`, so a factor applied after that comparison would fight it). Do it
through a registry the headset build fills — the same shape as `VrPolicy` — so other flavours
see a factor of 1. Verify by logging `AndroidUtilities.density` after `LaunchActivity.onCreate`
and by measuring one `dp(64)` view in pixels on the device.

### A-02 · high · Half the notifications never meet the gate

**FIXED** at `72f2f218` — the gate moved into `appendMessage`, before the de-duplication loop. Device check still owed.

The gate sits in `processNewMessages` (`NotificationsController.java:1055`), which handles
**live** updates. There is a second intake: `processLoadedUnreadMessages`
(`NotificationsController.java:1515`), which runs when the client starts or reconnects, loads
what is unread, calls `appendMessage` at `:1583` and `:1671`, adds to `total_unread_count` at
`:1686`/`:1691`, and shows notifications at `:1720`. On a headset that sleeps and wakes, this is
the *dominant* path — and it bypasses the silence profile entirely. The first thing a user sees
after putting the headset back on is the stack of banners the product promised not to show.

Both paths converge on one private method:

```
NotificationsController.java:1371   private void appendMessage(MessageObject messageObject)
callers: 1245 (processNewMessages), 1583 and 1671 (processLoadedUnreadMessages)
```

Fix: move the `VrPolicy` call into `appendMessage` and remove it from `processNewMessages`.
One hook again, now at the true choke point. `total_unread_count` in the loaded-unread path is
computed from the `dialogs` argument, not from `pushMessages`, so the launcher badge is
unaffected — state this in the code comment, because the next reader will ask.

### A-03 · high · The digest is write-only and holds onto message spans

**FIXED** at `31a8273b` — `DigestActivity` exists and is reachable; `lastText` is a truncated `String` and entries cap at 200 dialogs.

### A-08 · medium · Tablet layout is undecided, and the density fix will decide it by accident

**MEASURED 19 September 2026 on a Quest 3, and the premise below was wrong.** The panel reports
**`sw640dp`**, above the 600 threshold, so **the app runs in tablet mode** — and it does so
*whatever* the headset scale is set to.

The reasoning in the original finding assumed that multiplying density by 1.54 would divide the
panel's dp width and could drop it under 600. It cannot. The multiplier is applied to
`AndroidUtilities.density`, which governs what `dp()` returns inside the app; the system
`Configuration` that decides resource qualifiers is untouched and keeps reporting 200 dpi and
`sw640dp`. So the two are independent: the interface is drawn 1.54× larger *and* Android hands
it the tablet resource set. Confirmed from both sides — `dumpsys activity activities` prints
`sw640dp w1024dp h640dp 200dpi`, and `aapt2 dump resources` on the built package prints
`bool/isTablet` as `() false` / `(sw600dp) true`.

What that costs is still open, and it turns on a second condition: `LaunchActivity`'s onMeasure
takes the two-column branch only when `!AndroidUtilities.isInMultiwindow`, and the panel's
windowing mode **is** `multi-window`, so the split is most likely collapsed into one full-width
column. That last step is unmeasured — the split layout only appears once an account is signed
in, and the sign-in screen is not it.

The decision, when it is taken, needs no new code: upstream already carries
`SharedConfig.forceDisableTabletMode` (`SharedConfig.java:262`, read at `:627` with default
`false`, toggled at `:1384`), and `isTablet()` is `isTabletInternal() && !forceDisableTabletMode`
(`AndroidUtilities.java:2980`). Defaulting it to `true` in the headset build is a one-line
change behind the same kind of inert seam the density fix uses. **Do not make it before seeing
the signed-in layout**, because on this panel the platform may already be doing the right thing,
and a switch flipped against a measurement nobody took is how the original premise here went
wrong. *Answered in full on 19 September, from inside the headset.* Signed in, the panel showed the
menu eating roughly three fifths of the width with the conversation squeezed into the rest — so
`isInMultiwindow` is **not** what the windowing mode suggested, the split does happen, and the
guess above was the right thing to refuse to act on. The fix is the switch this finding already
named: `VrLayout` (headset module) sets `forceDisableTabletMode` once per install, leaving the
two-column layout reachable from the headset settings for anyone who wants it. Confirmed on the
device after restart — `mainconfig.xml` reads `forceDisableTabletMode=true`. A third mode, a
narrow rail of avatars beside an open chat, was asked for in the same breath and is **P-19**.

### A-20 · high · The interface scale was derived from a panel that does not exist

**FIXED** — the scale is re-based on the measured panel, the default is the platform's own
density, and the setting now states its consequence in chats rather than in adjectives.

Reported from inside the headset once the layout was single-column: *«видно только четыре чата
и много по ширине»*. The arithmetic reproduces it exactly, which is how we know the model is
right and the number was wrong:

```
panel            800 px tall, system density 1.25
old factor       1.54           -> app density 1.925 px/dp
height in dp     800 / 1.925    =  415.6 dp
minus chrome     - 48 action bar - 44 folder strip
over DialogCell    / 70 dp      =  4.6 rows        <- "four chats"
```

`VrDensity`'s own header stated the premise: *"the panel is 1440x900 dp at 1.3 m covering 52
degrees, so one dp is 0.881 mm, which is 2.33 arc-minutes"*. The real panel is **1280×800 px at
200 dpi** — 1024×640 dp before any scaling of ours. The derivation was arithmetic on an invented
measurement, and the invented figure was larger than reality in exactly the direction that costs
content.

**What changed.** The steps are now absolute multipliers on the system density — `0.85`, `1.0`,
`1.25`, `1.54` — instead of `{0.85, 1.0, 1.2} × 1.54`. The default is **1.0**: the density the
platform already chose for a panel. The old 1.54 survives as the largest step for anyone sitting
far from it, because a headset panel is virtual and its angular size is the wearer's to change by
moving it — a better lever than a constant compiled into an app. The preference key is renamed
`density_step_v2`, deliberately, so a saved "normal" from the old scale cannot silently become
the largest step.

**What it buys, by the same arithmetic, now pinned in `VrDensityTest`:** 9 rows at 0.85, **7 at
the new default**, 6 at 1.25, 4 at the old one. The regression test asserts the old default still
produces 4, so any future change that walks the default back there fails in CI rather than in a
headset a day later.

**And the setting says so.** The density row and its chooser read *"Balanced — about 7 chats"*,
with the count computed from the panel in front of the user through a pure
`VrDensity.rowsForFactor(panelHeightPx, systemDensity, factor)`. A scale named only by size asks
a person to imagine the result; this one states it, and the thing it states is exactly what was
complained about.

**Not changed:** `MIN_TARGET_DP` stays 64 and is still never multiplied by the step. Ray jitter is
a property of the hand; trading legibility for rows is the user's call, a smaller hit target is
not.

### A-21 · high · The panel was landscape because this fork asked for landscape

**FIXED** — the headset manifest now declares `portrait`, and Horizon OS reshaped the panel from
**1280×800** to **500×800**.

Reported from inside the headset after the scale was re-based: the list was fine top to bottom,
but a message stretched across the whole width, so a chat showed one long line and almost nothing
vertically. A messenger is a tall column of short lines — that is why every phone client is
shaped like a phone.

The cause was ours, one line, and it had a comment defending itself:

```xml
<!-- Landscape and resizeable: the system owns the panel's size, the app must not fight it. -->
android:screenOrientation="landscape"
```

The comment was true and was then used to justify its own opposite. Horizon OS sizes a 2D panel
**from the orientation the app declares**, so declaring landscape is precisely how an app fights
for a shape — and the shape it won was wrong. `resizeableActivity` stays `true`, which is what
"the system owns the size" was supposed to mean.

**Measured after the change:**

```
before   mBounds=Rect(0, 0 - 1280, 800)   sw640dp w1024dp h640dp  lrg land
after    mBounds=Rect(0, 0 -  500, 800)   sw400dp  w400dp h640dp  nrml port
```

400 dp wide is a phone. Two consequences worth naming:

- **`sw400dp` is below the 600 threshold**, so Android no longer hands the app the tablet
  resource set at all. A-08's `forceDisableTabletMode` default is now belt-and-braces rather
  than the only thing standing between the user and a split panel — worth keeping, because the
  panel is resizable and a wide one would cross the threshold again.
- **The row count helper was wrong the moment the panel turned**, and it was caught here rather
  than by a user: `panelHeightPx()` took `min(displaySize.x, displaySize.y)`, which is the height
  only in landscape. In a 500×800 portrait panel the smaller side is the *width*, so every
  density step would have advertised four chats instead of seven. Now it reads `displaySize.y`,
  which is the height in whatever orientation the panel is in, and the test constant carries a
  note saying the height is 800 either way.

### A-22 · medium · Every cold start flashes a white panel

**FIXED** — the headset build launches into Telegram's own night background instead.

Upstream's `Theme.TMessages.Start` (`TMessagesProj/src/main/res/values/styles.xml:6`) inherits
`Theme.AppCompat.Light` and sets `android:windowBackground` and `android:colorBackground` to
white, so the launch window is white until the first frame is drawn. On a phone that is a blink.
In a headset it is a lit panel at arm's length, usually in a dark room, in a client whose entire
premise is staying quiet and dark — and the device's own configuration reports `night`.

**The fix is a new style name, not an override, and that was learned the hard way.** Redefining
`Theme.TMessages.Start` in the headset module was tried first and *lost the resource merge*: the
module's own `packaged_res` and the incremental merge directory both held our version, and
`aapt2 dump resources` on the built APK still reported
`parent=style/Theme.AppCompat.Light` with `size=11` and white backgrounds. Rather than argue
with the merge, the headset build declares `Theme.NicegramVR.Start` and points
`android:theme` at it from its own manifest with `tools:replace`. Verified in the package:

```
style/Theme.NicegramVR.Start  parent=style/Theme.AppCompat
  android:colorBackground   = @color/vr_launch_background   (#0E1621)
  android:windowBackground  = @color/vr_launch_background
AndroidManifest  application  android:theme = @0x7f110135   <- that style
```

The colour is Telegram's own night background, so the launch window and the first drawn frame
are the same value and there is no step between them.

**Worth keeping as a rule:** an app module redefining a library's style by name is the obvious
move and it silently did not work here. Check the built artefact, not the merge directory.

### A-23 · high · The brand accent lasted exactly one session

**FIXED** — the colour is now re-asserted on every start, because nothing persists it.

Caught on the headset immediately after the theme shipped, and the build could not have shown
it. `VrTheme` set the Night theme's accent 10 to `#8B5FF2`, selected it and saved. The device
then reported:

```
$ adb shell run-as my.nicegram.vr cat shared_prefs/themeconfig.xml
    <int name="accent_current_night.attheme" value="10" />     <- the selection persisted
    (no colour anywhere)                                        <- the colour did not
```

Two causes, one behind the other. The first was mine: `saveThemeAccents(theme, true, false,
**true**, false)` — `indexOnly=true`, copied from `ThemeActivity` where only the selection
changes. The second survives fixing the first: with `indexOnly=false` upstream does write
`accents_night.attheme`, and decoding that blob on the device gives
`09 00 00 00 00 00 00 00` — an id record with **no palette in it**. Upstream keeps accent 10's
colour in a literal array in `Theme.java` and rebuilds it at startup.

So a slot repainted once reverts on the next launch, and the brand colour would have been
visible only in the session that set it — the sort of defect that survives every test, every
package inspection and a first glance on a device.

**The fix separates the two acts.** Selecting accent 10 stays a first-run default, so a user who
picks another accent keeps it. Setting slot 10's *colour* happens in
`QuestApplicationLoader.onCreate` on **every** start, so whoever has that slot selected always
gets Nicegram's purple rather than a slot that means one thing today and another tomorrow.

**The lesson is the one this repository keeps relearning:** the artefact is not the evidence.
The APK carried the right code and the right colours; only the device showed what the code did
on the second run.

### A-24 · high · The dark theme was applied on every start and saved on none

**FIXED** — `applyTheme(night, true, **false**)`, and auto-night turned off once at install.

The operator reported the theme "being overwritten, and it is not clear why". It was not being
overwritten: it was never written. `VrTheme.applyDefaults()` called

```java
Theme.applyTheme(night, /* save */ true, /* nightTheme */ true);
```

and upstream's own body of that method is

```java
if (!nightTheme && save) { editor.putString("theme", themeInfo.getKey()); }
```

The third argument does not mean "this is a dark theme". It means "this is the theme to use
*at night*" — and it **skips the branch that persists the choice**. So the theme was correct
for exactly as long as the process lived, and the next cold start read no `theme` key and fell
back to Telegram's default.

A second mechanism worked in the same direction. `selectedAutoNightType` defaults to
`AUTO_NIGHT_TYPE_SYSTEM` on SDK 29 and above (`Theme.java:4252`) and Horizon OS is 34, so the
client followed the headset's own day/night state and could switch away from whatever had been
chosen. It is now set to `NONE` once per install — a default, not a lock: a user who wants the
system to drive the theme can still say so in settings.

Measured, on the simulator, in the file that decides it:

so a match still reports the line it starts on — with `[^;]` bounding the match to one statement
so an unrelated upstream `getString` earlier in a method cannot reach forward and accuse it. The
strengthened guard was watched failing against the defect re-planted at `VrSettingsActivity:412`
before it was believed.

**What this says about the method.** Three findings now share one shape — A-26, A-29, A-31,
A-36 were all "the rule is right and the caller never asks it". This is its sequel: the rule
about the rule was right, and could not see far enough to apply it. A guard written against one
example of a defect tends to match that example's formatting.

### A-39 · high · A Russian interface turned English wherever the app names itself

**FIXED** — the rename substitutes the product's name into the sentence the pack returned,
instead of replacing the sentence.

`VrBrandNames` held forty-seven entries, and forty-two of them were finished **English**
sentences: `"Update " + PRODUCT`, `"Enter your " + PRODUCT + " passcode"`,
`PRODUCT + " uses %s of your device storage."`. `VrBrand.rename` runs *after* the cloud pack has
answered — that is the whole reason it exists, because the pack says "Telegram" for `AppName` in
every language — so each of those entries threw away a sentence the pack had already translated
and put English in its place. A Russian user saw Russian everywhere except the places this
client speaks about itself: the update prompt, the lock screen, storage, the call banner, the
permission prompts, the empty state.

The eleven remaining entries were worse in a quieter way. They were read at install with
`context.getString(my.nicegram.vr.R.string.…)`, which never asks the pack at all, so they were
English by construction; and the file's own comment said "P-18 fixes all of them together by
loading the keys into the pack", which was **false** — P-18 loads this module's keys into the
pack, and a `Context` read would still not have asked it.

**What it does now.** Two kinds of entry, and the difference is stated in the class header:

- A **rename** (36 ids) keeps upstream's sentence and puts this product's name where the
  service's was. `VrBrandNames.substitute` is pure, so the rule is seven assertions rather than
  a comment, and it falls back to the English sentence when the name is not in the value to
  replace — true, at the cost of its language, which is the right way round.
- A **replacement** (11 ids) is one of this module's own sentences standing in for upstream's,
  because the original said something this client must not say. Those are read by entry NAME
  through `LocaleController.getServerString`, which does **not** pass back through the rename
  seam (`LocaleController.java:1479`), so there is no recursion and they become translatable the
  moment P-18 loads the keys.

**Measured, and now asserted:** all 36 substitution ids name the service in upstream's own
`strings.xml`, so the substitution fires for every one of them.
`BrandSubstitutionTest.everySubstitutionIdIsAStringThatNamesTheService` fails if an upstream
merge rewords one — watched failing against a planted id (`NewGroup`) before it was believed.

`VrBrand` stopped holding a map and now holds a delegate: deciding what a string becomes needs
the value the pack just returned, and that decision belongs to the module that owns the list.
The hot path is still one volatile read and a null check on every flavour that installs nothing.

**One entry moved category after the fix, and the reason is a lesson about substitution.**
Upstream's `TelegramVersion` is not "Telegram %1$s" — it is **"Telegram for Android %1$s"**, so
substituting the name into it gives "Nicegram VR for Android 0.1.0": true of the package and odd
on a headset. That one is a replacement now, reading `vr_app_version` from this module's own
resources, which leaves 35 renames and 12 replacements. Substitution keeps the sentence it was
given, and that is the point of it — so an entry whose sentence says more than the name has to
be read before it is listed. Held against the constant by
`BrandSubstitutionTest.theVersionStringStillNamesTheProduct`, because the product's name now has
one copy outside `VrBrandNames.PRODUCT`.

### A-40 · high · A QR code on a headset panel cannot be scanned, and the screen did not fit

**FIXED** the same day it was written — one code instead of two, a ScrollView, and the path
that actually works promoted above it.

This finding is about the previous commit, `9d3d955a`. The phone-app offer was built around two
QR codes on the reasoning that "the phone that would install the app is already in the room".
That reasoning is false, and the way it is false is worth keeping: **the panel is inside the
headset.** A phone camera has nothing to point at, and the person wearing the headset cannot see
the panel and their phone at the same time. Six store screenshots were once "verified" by hash
(A-35); this is the same failure one level up — a mechanism checked for compiling rather than
for working.

**What the screen does now.** Its first button sends both store links to **Saved Messages**. The
account in this headset is the account on that phone, so the link is on the phone seconds later
— and that is a thing only a messenger can do, which makes it the right answer here and nowhere
else. `SendMessagesHelper.SendMessageParams.of(text, selfId)`, with a bulletin either way: a
send that fails says so rather than looking like it worked.

The code is kept, because it was asked for and because a headset CASTING to a phone or a
television does put the panel on a real screen. It is the third path now, it carries the short
address `nicegram.me/download` as text beside it for anyone reading rather than scanning, and
its own caption states the condition under which it can be scanned at all.

**And a second defect the same review found: it did not fit.** The two code blocks were
140 dp plus 12 dp padding on each side — 328 dp — inside a column with 24 dp padding. The Quest
3 panel is 500 x 800 px at 200 dpi and `VrDensity.STEP_SCALE` multiplies density by up to 1.54,
so the interface is between 400 and **260 dp** wide: 212 dp of usable width at the largest step.
The codes overflowed at three of the four steps and were tight at the fourth. Vertically the
content came to roughly 434 dp against 415 dp of panel, with no `ScrollView` — the buttons were
off the bottom with no way to reach them.

One 160 dp code centred, and a `ScrollView` with `fillViewport`. The sizing comment in
`MobilePromoActivity` now names the narrowest panel the build can produce rather than the
widest, which is the only one worth designing against.

**And the first-run screen had the same defect, which is how a class of bug is found rather
than an instance.** `FirstRunActivity` laid four paragraphs and a button row into a fixed
column with no scroll. In English at the default step it fits; at the largest step, or once the
text runs to Russian length, the row that DISMISSES it goes past the bottom of the panel — on
the first screen of the product, with no way to scroll to it. It is a `ScrollView` now too, and
`setGravity(CENTER_VERTICAL)` with `fillViewport` keeps the centred look it had when the
content is short.

`ScrollableScreensTest` is the guard: every `*Activity` in this module that extends
`BaseFragment` must name a scrolling container. Three of the five already did, because a list
scrolls by itself; the two that did not were the two that were broken. Watched failing against the
exact version of `FirstRunActivity` this change replaced, restored from `HEAD` so that it
compiled — the first attempt renamed the class instead and only broke the build, which
proves nothing about the test.

### A-41 · high · P-10, the QR sign-in, rests on the premise A-40 disproved

**PLAN CHANGED**, no code written — which is the point of finding it now rather than after five
to eight days of work.

`plan.md` P-10 and `roadmap.md` both describe sign-in as: *"The headset displays, the phone
scans."* That is the same assumption as A-40 and it fails for the same reason — **the panel is
inside the headset**, so there is nothing for a phone camera to point at, and the person wearing
it cannot see the panel and their phone at once.

It is not a detail of the design; it is the whole flow. Telegram's QR login is always the new
device exporting a token and rendering it (`auth.exportLoginToken`) while an **already
authorised** device scans it. There is no variant in which the headset scans, and the token is a
long base64 blob, so there is no variant in which it is read aloud or typed either.

**What the estimate was actually buying.** The pain P-10 names is real — typing a phone number
with a ray is the worst interaction in this product. What it is not is unaddressed:

- **A Bluetooth keyboard works.** Meta's own keyboard-overlay page opens by saying so ("While
  you can use physical Bluetooth keyboards for text entry on a Meta Quest headset…",
  `documentation/unity/unity-keyboard-overlay.md`, read 23 September 2026).
- **Dictation is already built here** (P-11, P-12) — a provider layer and a composer trigger.
  Pointing it at the phone-number field is a far smaller change than a new login page.
- **Casting** makes the QR work for whoever wants it, the same exception A-40 kept the code for.

**Decision.** P-10 is not started. Phone-number sign-in stays the path; the QR page is
reconsidered only if casting turns out to be common, and the ray-typing pain is answered by
dictation on the login field instead. The TL constructors and the renderer stay listed, because
they are correct and cost nothing to leave written down.

**What this says about the method.** Three findings in one day — A-40, this, and the layout half
of A-40 — come from asking of each screen "and then what does the person physically do?" That
question has no representation in a compiler, a unit test or a hash, and both the store
screenshots (A-35) and this passed every check that does.

### A-42 · medium · A Quest build compiles four ABIs and packages one

**FIXED** by `-PquestAbiOnly`, which both CI workflows now pass. The default is unchanged and
waits on Q-03.

Found because the machine ran out of disk and the build failed like this:

```
StarAppsSheet.java:28: error: error while writing <anonymous ...>:
  .../classes/org/telegram/ui/Components/StarAppsSheet$1.class: No space left on device
```

A `javac` **error** on a file nobody had touched. It reads exactly like a code defect and is not
one; `df -h` said 415 MiB free of 460 GiB.

**The cause is one layer in from where it looks.**
`TMessagesProj_AppQuest/build.gradle:204` sets `abiFilters "arm64-v8a"`, and it is natural to
read that as "this build compiles one ABI". It does not. `abiFilters` on the application decides
what is **packaged**; the library module `TMessagesProj` has no filter of its own, so CMake
compiles `armeabi-v7a`, `arm64-v8a`, `x86` and `x86_64` on every build, and the Quest APK throws
three of them away.

**Measured, twice, because the first measurement was wrong.** The three unused ABI trees were
deleted to free 8.3 GB, and `CONTRIBUTING.md` was updated to say that deleting them costs
"none for this build". The next `assembleQuestDebug` rebuilt every one of them and ended with
1.6 GB free — so the note was not merely incomplete, it was advice that does not work. Deleted
again with `-PquestAbiOnly`: 5.7 GB freed, and after a successful build `.cxx/Debug` holds
`arm64-v8a` and nothing else, with free space having gone **up** rather than down.

**What it bought, as one observation rather than a controlled measurement.** The first CI run
carrying the flag finished in **11.5 minutes**; the two full successful runs before it took
**24.8** and **42.2**. CI caches the native build between runs and those three runs did not carry
the same cache, so this is a signal and not a benchmark — but it points the way the arithmetic
says it should, and no run since has been slower.

**Why the default did not change.** The Huawei and standard flavours are built from the same
module and need all four ABIs. Whether they stay maintained in this fork is A-06 — an operator
decision, `plan.md` Q-03. Both CI workflows build only the Quest APK, so they take the flag
unconditionally; a developer building another flavour is unaffected.

**And one thing done wrongly, recorded so it is not repeated.** `~/.gradle/caches/build-cache-1`
was deleted in the same pass to free 1.1 GB. The next build took **35 minutes**. A build cache is
not a candidate for reclaiming space on a machine that builds this project.

### A-43 · critical · A client that promises silence rang for anyone who called

**FIXED** — `VoIPService.startRinging` asks `VrPolicy.allowsCall`, the same gate messages pass.

The silence gate sits in `NotificationsController.appendMessage`. **A call does not go through
it.** So the whole of this product's promise — "nothing arrives until you say it may. Name the
people, chats and words worth interrupting you" — was false for the single loudest thing the
device can do, and false for every caller in the world rather than for an edge case.

**It is not hypothetical.** Read from the APK: `RECORD_AUDIO`, `MANAGE_OWN_CALLS` and
`FOREGROUND_SERVICE_MICROPHONE` are all present, the whole `voip/` stack is compiled in, and
`startRinging` is reachable. Voice calls work in this build whether or not anyone planned them.

**The plan said calls were out of scope, and that sentence was half right.** "Calls and video
calls from the headset (no forward camera; a different product)" — the camera argument settles
*video* calls and says nothing about voice, which ships regardless. A feature can be excluded
from a plan and still be in the binary; only the binary rings.

**The fix is one question at one choke point.** `startRinging` (`VoIPService.java:4501`) is the
only entry for an incoming private call, and both of its branches end in
`startRingtoneAndVibration`, so gating there covers the ringtone and the notification together.

**The call is not declined.** `dispatchStateChanged(STATE_WAITING_INCOMING)` still runs, the
caller still hears ringing, and Telegram delivers the missed call into the chat as a service
message — which arrives through `appendMessage` moments later, is gated like any other message,
and lands in the digest. So nothing is lost by not ringing except the interruption, which is
what the user asked for by silencing the device. That is also why the gate needs no second
suppression channel for calls: adding one would show the same missed call twice.

**The rule** is `SilenceDecision.allowCall` — master switch first, then the named people and
chats. Words are not consulted: a call carries no text, and matching a caller's name would be a
different feature nobody asked for. A caller is checked against `chats` as well as `people`
because a one-to-one dialog id **is** the other person's user id, so someone who named the chat
has named its only other participant.

Six assertions in `CallDecisionTest`, and `VoIPService` is now in `SeamAnchorsTest`'s list so the
edit cannot be lost to an upstream merge in silence.

*Still owed on a device, and it is P-21's first item: nobody has ever placed or received a call
on a headset. This makes the rule right; it does not prove the ring works at all.*

**Two documents in this repository disagreed about whether calls exist, and the binary sided
with the listing.** `plan.md` excluded them as "a different product", while
`store/listing-en.md` had been telling prospective users, under **WHAT IT DOES NOT DO**, that
"messages **and calls** reach you while it is running". The listing was right. A feature can be
absent from the plan, present in the package, and described to the public, all at once — and the
only one of the three that rings is the package.

**The same listing carried two claims that were false until 23 September**, both now true:

- *"Notifications are off when you start. Nothing reaches you until you decide it should."* —
  false for every caller in the world until this finding.
- *"Dictation turns speech into text you read before it is sent."* — there was no way to dictate
  into a chat until P-12; dictation existed only as a settings screen that proved the service
  worked.

That listing is what a content reviewer judges "completeness and value" against. Submitting it
before today would have been submitting two claims the build did not honour.

### A-44 · high · Leaving a chat mid-sentence left the microphone held

**FIXED** the same day it was written, in the code written that morning.

`DictationButton` (P-12) holds a `VoiceRecorder`, which holds an `AudioRecord` and a capture
thread for up to sixty seconds. Nothing stopped it when the view went away. Close the chat
while dictating and the microphone stayed held by a control that is no longer on screen — with
the system's recording indicator lit and **nothing anywhere to press to stop it**. On a headset
that is worse than on a phone: there is no notification shade to go looking in.

Found by re-reading the morning's own code rather than by anything failing, which is the only
way this one could have been found — no compiler sees it, no unit test of a `View` reaches it,
and on a device it looks like the headset deciding to listen to you.

`onDetachedFromWindow` now cancels. **`cancel()` rather than `stop()`**: somebody who left the
chat did not ask for text in it, and putting words into a field they walked away from is its own
surprise.

**And off the main thread.** `VoiceRecorder.stop` joins the capture thread with
`t.join(2000)`. In practice the loop exits immediately — it checks a volatile flag — but a
detach is a screen transition, and up to two seconds of frozen interface at that exact moment is
not a risk worth taking for a tidier call site. `DictationActivity.onFragmentDestroy` had the
same shape and the same hazard, one line older, and is posted to the background queue too.

`VoiceRecorder.stop` now says in its own javadoc that it blocks, so the next caller does not
have to find out.
