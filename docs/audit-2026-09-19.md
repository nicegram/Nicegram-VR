# Audit — 19 September 2026

What is actually true of this repository at `a29d5040`, established by reading upstream code
and measuring artifacts rather than by recalling what was intended. Every finding names the
line it rests on. The remediation is in [plan.md](plan.md); this file says what is wrong and
why, and what was checked and found sound so nobody re-audits it.

**Method.** Each headset-layer claim was traced into the upstream code it depends on
(`grep`/`sed` on `TMessagesProj`), each artifact claim was read from the artifact (APK dex,
generated `BuildConfig`, vault slot lengths, build log), and each design claim was measured in
the mockups (52 states × 3 densities, WCAG contrast computed from `tokens.css`). Nothing was
run on a headset; every finding marked *device* below is a measurement still owed.

## Findings

Severity: **critical** — the product's stated behaviour is false; **high** — a user will hit
it; **medium** — a contributor will hit it or a document is now untrue; **low** — hygiene.

### A-01 · critical · The density scale is silently thrown away

`VrDensity.apply()` multiplies `AndroidUtilities.density` in `QuestApplicationLoader.onCreate`
(`TMessagesProj_AppQuest/.../QuestApplicationLoader.java:23`). Then
`AndroidUtilities.checkDisplaySize` reassigns it from the display metrics:

```
AndroidUtilities.java:2751   density = context.getResources().getDisplayMetrics().density;
```

and is called from `LaunchActivity.java:409` (activity `onCreate`, before any UI),
`LaunchActivity.java:7117` (`onConfigurationChanged`) and `ApplicationLoader.java:382`. The
multiplication happens once, before all three; the first one erases it. **The readability
feature this fork is named for does nothing in the shipped APK.**

Fix: apply the factor *inside* `checkDisplaySize`, immediately after the assignment and before
`newDensity` is read (the method compares old and new density to decide on
`Theme.reloadAllResources`, so a factor applied after that comparison would fight it). Do it
through a registry the headset build fills — the same shape as `VrPolicy` — so other flavours
see a factor of 1. Verify by logging `AndroidUtilities.density` after `LaunchActivity.onCreate`
and by measuring one `dp(64)` view in pixels on the device.

### A-02 · high · Half the notifications never meet the gate

The gate sits in `processNewMessages` (`NotificationsController.java:1055`), which handles
**live** updates. There is a second intake: `processLoadedUnreadMessages`
(`NotificationsController.java:1515`), which runs when the client starts or reconnects, loads
what is unread, calls `appendMessage` at `:1583` and `:1671`, adds to `total_unread_count` at
`:1686`/`:1691`, and shows notifications at `:1720`. On a headset that sleeps and wakes, this is
the *dominant* path — and it bypasses the silence profile entirely. The first thing a user sees
after putting the headset back on is the stack of banners the product promised not to show.

Both paths converge on one private method:

```
NotificationsController.java:1371   private void appendMessage(MessageObject messageObject)
callers: 1245 (processNewMessages), 1583 and 1671 (processLoadedUnreadMessages)
```

Fix: move the `VrPolicy` call into `appendMessage` and remove it from `processNewMessages`.
One hook again, now at the true choke point. `total_unread_count` in the loaded-unread path is
computed from the `dialogs` argument, not from `pushMessages`, so the launcher badge is
unaffected — state this in the code comment, because the next reader will ask.

### A-03 · high · The digest is write-only and holds onto message spans

`Digest` accumulates suppressed messages, but nothing reads it: `digest()` has no callers
outside its own declaration. There is no digest screen (SCR-24), no count in the header. The
whole reason to suppress rather than drop — "you can see what accumulated" — is unimplemented.

Also `Digest.Entry.lastText` is a `CharSequence` assigned from `message.messageText`
(`Digest.java:24`, `:46`). Telegram's message text is frequently a `Spannable` carrying
spans that reference other objects; keeping it alive for the session is a retention leak.
Store `String.valueOf(...)`, truncated.

### A-04 · high · The README says something that was never done

`README.md:10`: "The repository builds and installs." It builds. Nothing has been installed
anywhere; the headset was unreachable for the whole session. Change the sentence.

### A-05 · high · CI cannot pass, and when it can it will be slow

- No repository secrets are configured (`gh secret list` is empty), so the first compile task
  will stop on the missing keys as designed.
- `.github/workflows/build.yml:39` uses `actions/gradle-build-action@v3`, which is deprecated in
  favour of `gradle/actions/setup-gradle@v4`.
- Nothing caches the native build. Every run would recompile FFmpeg, BoringSSL, libvpx, dav1d
  and openh264 from scratch, against a 120-minute timeout.
- `actions/checkout` with `submodules: recursive` clones the thirteen submodules with full
  history; FFmpeg alone is large.

### A-06 · high · Every other flavour in the repository now compiles with an empty credential

`TMessagesProj/build.gradle:145` falls back to `"0"` when `TELEGRAM_APP_ID` is absent, and
`BuildVars` reads that for all flavours. `TMessagesProj_App`, `_AppStandalone`,
`_AppHockeyApp` and `_AppHuawei` therefore build to an APK that cannot connect. Upstream's
sample id was at least a working placeholder. Decide one of two things and write it down:
those flavours are unmaintained in this fork (say so in the README and remove them from
`settings.gradle`), or they get the same fail-by-name check the headset module has.

### A-07 · medium · No store metadata in the manifest

`TMessagesProj_AppQuest/src/main/AndroidManifest.xml` declares hardware features and the
landscape activity, and deliberately nothing Horizon-specific (supported-device declaration,
VR/2D launch category), because the exact keys were not going to be written from memory. That
was correct at the time and is now a gap: the answer to VRQ-001 (store policy) and the current
documentation decide these together.

### A-08 · medium · Tablet layout is undecided, and the density fix will decide it by accident

Upstream's two-column layout is switched by `R.bool.isTablet`, which is `true` in
`values-sw600dp` and `values-sw720dp` and `false` in `values` (`AndroidUtilities.java:2949`,
`isTabletForce`). Multiplying density by 1.54 divides the panel's dp width by 1.54. Whether the
panel stays above 600 sw-dp after A-01 is fixed is unknown until measured; if it drops below,
the client becomes a stretched single-column phone layout, which is the worst of both. *Device.*

### A-09 · medium · The string registry and the shipped strings disagree

The registry (`nicegram-product-workspace/.../brand/strings.md`) has `silence.list.people` =
"Люди" and `silence.list.chats` = "Чаты" as two headers; the APK ships one,
`vr_silence_people` = "People and chats" (`strings_vr.xml:11`). The registry's
`mic.intro.body` names a "Nicegram server" as the recipient of dictation audio, but this
client's design sends audio to an endpoint the user configures — the sentence is false for
this product. Reconcile in one direction: the registry is canonical, `strings_vr.xml` is
generated or linted against it.

### A-10 · medium · `screens.md` says SCR-25 and SCR-26 are only designed

`design/docs/ux/screens.md:38-39` list both as `designed / none yet`. `SilenceRulesActivity`
exists and compiles. Per the contract that is `drifted` until an audit passes it, with
`Coverage` pointing at the file.

### A-11 · medium · Generation counter is a non-atomic increment on a volatile

`SilenceStore.java:61`: `generation++` on `private static volatile int`. Two concurrent saves
can lose an increment; the gate would keep a stale profile for one more message. Use
`AtomicInteger`. Cheap, and the current form is the idiom every reviewer flags.

### A-12 · medium · The exceptions screen is a list of names with nothing around them

`SilenceRulesActivity` renders people and chats under one header with `DialogObject.getName`,
which returns an empty string for a user or chat the client has not loaded yet — a blank row
the user cannot identify or remove with confidence. No avatar, no distinction between a person
and a group. Fix: preload with `MessagesController.getUser/getChat` and fall back to a visible
placeholder; split the two groups; use a cell with an avatar.

### A-13 · medium · The Notifications row shows a title and nothing else

`VrEntryPoints.SettingsRow` exposes only `title()`. The row cannot show "3 exceptions", and a
first-run user has no reason to open Notifications at all. Add a `value()` to the seam and
build SCR-06, which is the screen whose whole job is to point here.

### A-14 · medium · `lintOptions` is deprecated

`TMessagesProj_AppQuest/build.gradle` uses `lintOptions {}`; AGP has replaced it with
`lint {}` and will remove the old block. Migrate before it becomes the reason a build breaks.

### A-15 · medium · The architecture decision in Dataroom is stale

`dataroom/docs/architecture/nicegram-vr-quest-20260919.md:3` still opens with "Кода нет".
There is code. The status line needs the date and the revision it was last true at.

### A-16 · low · No theme descriptions on the new fragment

`SilenceRulesActivity` does not override `getThemeDescriptions()`, so a live theme switch
leaves it in the old colours until reopened. Upstream fragments all do this.

### A-17 · low · Nothing rejects Telegram's public sample credential

The key check refuses *empty* values. It would accept `4` / upstream's sample hash, which
would build and then fail against the network. Rejecting exactly that pair is a two-line
guard that turns a confusing runtime failure into a build-time sentence.

### A-18 · low · Rendered documentation can drift from its source

In the product workspace, `design/docs/**/*.html` are generated from `*.md` by
`design/docs/render.py`. Nothing in `npm run check` re-renders and compares, so an edit to
the Markdown that forgets the render step ships a stale page.

## The recurring audit — run this after every change

1. `./gradlew :TMessagesProj_AppQuest:testQuestDebugUnitTest :TMessagesProj_AppQuest:assembleQuestDebug`
2. Read the APK, not the log: ABI list, application class, presence of the expected string.
3. Leak check on the build log: count of 32-hex tokens and 8-digit numbers must be 0.
4. `git diff --cached --name-status | grep '^D'` must be empty before every commit.
5. Mockups: 52 states × 3 densities, targets ≥ 64 dp, text ≥ 20 dp at normal.
6. Documentation: every `designed`/`none yet` in `screens.md` still true; `render.py` re-run.
7. On a device, in this order: starts and stays up 30 min → sign-in → chat list holds frame
   rate → nothing notifies → one exception notifies and only it → **the phone's notification
   settings did not change** → sleep the headset, message it, wake it: the digest shows and
   the banners do not.
